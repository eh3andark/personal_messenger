# Security notes and threat model — چت امن

## What the implementation protects

The app encrypts **new** message bodies, conversation-preview text and Drive notes with AES-256-GCM. A completed newly uploaded file is sealed in independently authenticated 1 MiB blocks under a key derived from the server's randomly generated master secret and the file identifier. Completed encrypted media supports authenticated byte-range playback; decryption/authentication failure is an error, not silent plaintext fallback. Passwords created through the supported account flows are hashed with Bcrypt. Login sessions are stored as server-side token records in protected `data/`; state-changing API requests require an authenticated header token (cookie-only cross-site forms cannot mutate data). JSON stores use file locks and atomic replacement; conversations roll over into numbered shards. Exact-ID account lookup, room membership checks, owner checks and channel posting restrictions are enforced server-side. Admin-controlled raw user JSON is validated for duplicate IDs, hash rules and reuse safety.

**Not end-to-end encryption (E2EE).** PHP must decrypt content to serve it. The site operator, a compromised server, or anyone with both the master secret and data files can read message content. This cannot protect against a compromised recipient device, a recipient saving/downloading messages, malicious server code, or an administrator with server-file access. Encryption at rest does not replace HTTPS. Do not advertise this product as E2EE or a zero-knowledge service.

## What remains visible, temporary or out of scope

- Member lists, usernames, room metadata, message times/IDs, file names/types/sizes, quota usage, relationship metadata and public Telegram preview text/link/CDN metadata in the protected cache are **not encrypted**. Temporary upload chunks/assemblies can briefly hold plaintext before encryption and stale chunks are removed opportunistically; protect the disk, backups and cPanel file access. Pre-existing plaintext media from earlier deployments is **not automatically migrated**.
- Chat members who had access can retain downloaded files, forwarded copies, screenshots and old backups. A sender deleting an upload «for everyone» removes **their** sent references in authorized chats; independently forwarded/referenced copies and recipients' local copies remain. «Only for me» does not delete the recipient's view. Quota is reclaimed only after the last reference to a media object is removed.
- Group invite links are bearer capabilities: sharing one grants join access until revoked. The token is placed in the URL fragment so the **initial** page request does not include it, but it can remain in browser history, clipboard, screenshots or shared links. Regenerate a private invite when exposed. Public rooms can be found by exact handle/ID **or by bounded search of public room names**; private rooms are excluded from public-name results and require valid invitations. The announcement channel is a mandatory all-user system room; only system admins may post, and members cannot leave or remove it from their dialog registry (archiving may still change which tab displays it). The first setup admin is a protected permanent direct-contact account. Admins of other channels control posting; message recipients and platform operators are still in scope of the server's trust model.
- Public Telegram previews are optional server-to-server fetches of `t.me/s/...` and allowlisted CDN media, not private Telegram access or a Telegram client. Remote servers see the host's IP. Available preview media may be compressed/lower quality, absent, expired or larger than import caps. Live markup and network policy can change without warning. Import attempts are capped and tied to recently cached channel/post identifiers, not arbitrary user-submitted URLs; DNS resolution and redirect targets are restricted to the expected public destinations. Errors are surfaced rather than silently claiming complete imports. Optional AI and web tools can disclose submitted text to external providers if enabled; configure them with informed consent and never commit API keys.
- Locally compressed video is processed in the browser only **after explicit user choice**. The browser codec/audio track may not be available; the UI offers an original-upload fallback. Static sticker creation converts the selected image locally before uploading; the resulting WebP is an ordinary quota-accounted media object.
- Presence is linked to open tab IDs: a page-close request removes that tab promptly; if the browser/network drops the request, the last heartbeat expires in about 35 seconds. A background-but-open page may remain online; blocked peers do not receive each other's presence. The browser only marks a chat read when it is actually opened, rendered and visible; a malicious authenticated client could still call the explicit read API itself.
- **Account activity metadata is not encrypted:** `data/user_activity.json` stores account creation and successful login times; `data/presence.json` stores heartbeat/last-seen times. Only the first setup admin can request the full account audit; user lists and the raw `users.json` API do not include these audit fields. The host operator, file-manager holder or someone who obtains `data/` can still inspect them, and peers may already see limited last-seen presence for permitted contacts. Back up both files with the **whole active data tree** and block their direct web access. Pre-upgrade creation time is unknowable unless previously recorded; `unknown` is not equivalent to `never logged in`. Online presence may mean a background tab, **not** confirmed reading or messaging. The audit refreshes on tab open or manual request, not continuously.
- Optional public TGJU rate boards are read without an API key. The app labels source, units, collection time and stale/unavailable states, but a fresh HTTP fetch cannot prove that a clock-only trading quote was updated today; external markup/access can change. Never treat this feature as financial advice or guaranteed real-time data.

## Non-negotiable deployment requirements

1. Require **HTTPS** and keep `.htaccess` effective. Apache/LiteSpeed rules block direct web access to `data/`, `core/`, hidden files and sensitive backups. Under Nginx or unusual proxies, implement equivalent denials manually **before going live**. Test actual HTTP GETs for `/core/bootstrap.php`, `/data/users.json`, `/data/user_activity.json`, `/data/presence.json`, `/data/.master_secret.php`, `/data/.htaccess` and backups: all should return 403/404, never code or file contents. The admin panel exposes a deployment check; verify using a browser too.
2. Do not publish `data/` from any live site or copy the one-time setup token, `.master_secret.php`, `users.json`, `user_activity.json`, `presence.json`, `config.json`, messages, media, session files, upload chunks, import cache or logs to GitHub. The packaged `data/` skeleton intentionally contains only protection/placeholder files. Keep the code and **entire** active data tree backed up together in private storage with restricted permissions. Losing the master secret makes ciphertext unrecoverable; losing data but keeping only the key does not reconstruct chats. Protect backups as strongly as the site.
3. Install from `hamrah-messenger-cpanel.zip` into a **new** directory. On upgrades, back up code + data and test on a disposable copy before replacing only code/config defaults. Never unpack the clean archive over an existing `data/` tree. Use strong unique passwords and restrict admin/cPanel access. Replace/delete the archive from the public web root after extraction.
4. The first admin is created only through `setup.php` with a random token written to `data/.setup_token.php`, read through a trusted file manager, not from a webpage. No default credentials. The setup route is disabled after the first admin. Make sure setup is unreachable in unintended copies of the site.
5. The 80%-quota threshold stops *new media* while allowing text. It is an operational limit, **not** an anti-DoS guarantee: the first upload crossing it can complete, simultaneous work consumes disk, and other hosting quotas/requests can still fail. Monitor disk usage, backups and PHP/Apache resource limits. Do not run the destructive HTTP test suites against live data.

## Responsible disclosure

If the maintainer has enabled **GitHub private vulnerability reporting**, use the repository's [private advisory form](https://github.com/eh3andark/personal_messenger/security/advisories/new) to send a report with reproduction steps, affected version and impact. If that option is unavailable, open a public issue asking **only for a private contact channel**—do not include exploit details, credentials, keys or private data. The maintainer should enable private vulnerability reporting before advertising the project. Rotate secrets and investigate backups if the server or master key has been exposed. This is a best-effort open-source deployment guide, not a formal security audit.

**گزارش محرمانه:** اگر گزینهٔ «Report a vulnerability» در [مخزن پروژه](https://github.com/eh3andark/personal_messenger) فعال شده، از فرم محرمانهٔ بالا استفاده کن. اگر فعال نیست، فقط یک Issue عمومی برای درخواست مسیر ارتباط خصوصی باز کن؛ **شرح آسیب‌پذیری یا اطلاعات واقعی را در Issue ننویس**.
